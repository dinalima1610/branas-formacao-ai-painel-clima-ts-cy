# ADR-005: Geolocation Resolves Places via Reverse Geocoding Endpoint

## Status

Accepted

## Date

2026-05-20

## Context

PRD requires an opt-in “Use my location” chip. Browser geolocation yields coordinates only; the product still needs human-readable place context and the same disambiguation rules as text search when multiple matches exist.

## Decision

After the user grants geolocation, the frontend sends coordinates to **`GET /places/reverse?latitude=&longitude=`**. The backend returns the same `PlaceCandidate[]` shape as search (max 5). The user picks a candidate when multiple matches exist, then the app calls **`GET /weather`** with the selected coordinates.

Coordinates are **not** sent directly to `/weather` without passing through place resolution when reverse geocoding returns multiple candidates.

## Alternatives Considered

### Alternative 1: Skip reverse geocoding — `/weather` with raw lat/lon

- **Pros**: One fewer HTTP call.
- **Cons**: No city label for UI; skips disambiguation near borders.
- **Why rejected**: User chose reverse endpoint flow.

### Alternative 2: POST `/weather/locate` aggregated response

- **Pros**: Mirrors single-endpoint search pattern.
- **Cons**: Diverges from two-step REST (ADR-002).
- **Why rejected**: User chose explicit reverse geocoding route.

## Consequences

### Positive

- Consistent UX between typed search and geolocation.
- Display name and region/country available before weather load.

### Negative

- Additional round-trip after browser geolocation success.
- Reverse geocoding accuracy depends on Open-Meteo coverage.

### Risks

- **Permission denied** — frontend shows neutral PT-BR message; manual search unchanged (PRD).
- **Poor GPS accuracy** — user may need to pick from disambiguation list or search manually.

## Implementation Notes

- Frontend: `navigator.geolocation.getCurrentPosition` only on chip click; never on mount.
- Backend: reuse geocoding client with reverse parameters per Open-Meteo Geocoding API.
