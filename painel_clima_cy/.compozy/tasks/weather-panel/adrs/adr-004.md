# ADR-004: Wind Speed Units Coupled to Temperature Unit Toggle

## Status

Accepted

## Date

2026-05-20

## Context

PRD open question: whether wind displays in km/h, m/s, or locale-driven units. The panel already requires a °C/°F toggle affecting all temperatures.

## Decision

Display wind speed **in lockstep with the active temperature unit**:

| Temperature unit | Wind speed unit | Label (PT-BR) |
|------------------|-----------------|---------------|
| Celsius (`celsius`) | km/h | `km/h` |
| Fahrenheit (`fahrenheit`) | mph | `mph` |

Open-Meteo `wind_speed_unit` query parameter maps accordingly on backend forecast requests. Frontend labels update when the user toggles units.

## Alternatives Considered

### Alternative 1: Fixed km/h always

- **Pros**: Simplest for Brazilian audience.
- **Cons**: Inconsistent when user selects °F.
- **Why rejected**: User chose coupled units.

### Alternative 2: Fixed m/s

- **Pros**: SI standard.
- **Cons**: Unfamiliar for general course audience; mismatched with °F.
- **Why rejected**: User chose coupled units.

## Consequences

### Positive

- Coherent mental model: “metric bundle” vs “imperial bundle”.
- Open-Meteo natively supports `wind_speed_unit` alongside `temperature_unit`.

### Negative

- Toggling units may require refetch or client-side conversion for wind if only temperature is converted locally.

### Risks

- **Extra `/weather` call on toggle** if both metrics refetched — mitigate by client-side temp conversion + wind conversion table, or accept refetch per ADR-003.

## Implementation Notes

- Pass `temperatureUnit` on `GET /weather`; service sets `temperature_unit` and `wind_speed_unit` on Open-Meteo forecast request.
- Document mapping in `WeatherService` and shared types.
