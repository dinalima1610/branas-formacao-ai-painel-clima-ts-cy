# ADR-002: Two-Step REST API for Place Search and Weather

## Status

Accepted

## Date

2026-05-20

## Context

The frontend must never call Open-Meteo directly. The PRD requires city search with disambiguation, optional geolocation, and a single weather payload (current + hourly + daily). Multiple API shapes were considered during TechSpec clarification.

## Decision

Expose **two read-only REST resources**:

1. **`GET /places/search`** — forward geocoding by city name; returns up to 5 place candidates.
2. **`GET /places/reverse`** — reverse geocoding from browser coordinates after explicit geolocation opt-in.
3. **`GET /weather`** — aggregated current conditions, 24 hourly intervals (1h step), and 3–5 daily summaries for a selected `latitude` / `longitude` and `temperatureUnit`.

The frontend always completes disambiguation (when needed) before calling `/weather`.

## Alternatives Considered

### Alternative 1: Single POST `/weather/search`

- **Description**: One endpoint returns either candidates or full weather depending on ambiguity.
- **Pros**: Fewer round-trips when unambiguous.
- **Cons**: Mixed response shapes complicate typing and error handling; harder to cache or document in OpenAPI.
- **Why rejected**: User chose explicit two-step flow.

### Alternative 2: Three endpoints (search, current, forecast)

- **Description**: Frontend merges current and forecast responses.
- **Pros**: Smaller payloads per call.
- **Cons**: Extra latency and state on the client; duplicates place context.
- **Why rejected**: User chose aggregated `/weather` after place selection.

## Consequences

### Positive

- Clear separation between place resolution and weather fetch.
- Stable contracts for Vitest and OpenAPI documentation.
- Geolocation reuses the same `/weather` path after reverse lookup.

### Negative

- Minimum two HTTP round-trips per successful search (search → weather).
- Controllers must stay thin; aggregation logic lives in services.

### Risks

- **Inconsistent query validation** across place endpoints — mitigate with shared query parsers in controllers.
- **Over-fetching on `/weather`** — acceptable for MVP; monitor payload size in QA.

## Implementation Notes

- Register routes in `backend/src/index.ts` or a dedicated router module wired from `index.ts`.
- Map Open-Meteo Geocoding API in `data/clients/open-meteo-geocoding.client.ts` and Forecast API in `data/clients/open-meteo-forecast.client.ts`.
- Document all three endpoints in OpenAPI (project convention).
