# ADR-001: Current Conditions Panel with Hourly and Daily Mini-Forecast

## Status

Accepted

## Date

2026-05-19

## Context

The product needs a weather panel integrated into the existing course demo application (`IA para Devs`). Users must search by city, resolve ambiguous place names, optionally use browser geolocation via a suggestion chip, view standard current conditions with a Celsius/Fahrenheit toggle, and see short-range forecast context. The backend must be the sole data source for the frontend; external weather data comes from Open-Meteo (no API key). The UI must follow the established warm editorial design system (`DESIGN.md`).

## Decision

Deliver **Approach B — Current conditions panel plus mini-forecast** as a single MVP:

- **Current conditions**: temperature, short condition label, visual weather indicator, feels-like, humidity, and wind speed.
- **Mini-forecast**: (1) next **24 hours** as a prominent hourly strip (temperature and condition per interval), and (2) a **3–5 day** daily summary below (daily min/max and condition).
- **City search**: free-text city input; when multiple places match, show a short disambiguation list before loading weather.
- **Geolocation**: optional chip/button (e.g., “Use my location”); user accepts or ignores; no automatic load without explicit acceptance.
- **Units**: user can toggle between °C and °F in the panel.
- **No** saved cities, favorites, or cross-session history in MVP.

## Alternatives Considered

### Alternative 1: Current Conditions Only (Focused Panel)

- **Description**: MVP limited to search, disambiguation, geolocation chip, standard current metrics, and unit toggle—no forecast sections.
- **Pros**: Smallest scope, fastest delivery, lowest risk of cluttered UI.
- **Cons**: Less useful for planning; does not meet stakeholder desire for forward-looking context.
- **Why rejected**: User selected a richer experience that includes forecast at launch.

### Alternative 2: Phased Visible Delivery (Metrics Later)

- **Description**: Phase 1 ships search and minimal display; Phase 2 adds full metrics, unit toggle, and geolocation.
- **Pros**: Reduces initial delivery risk.
- **Cons**: Delays the complete experience already specified; splits user testing across incomplete flows.
- **Why rejected**: User preferred a fuller first release with forecast included.

### Alternative 3: Hourly OR Daily Forecast Only

- **Description**: Add either 24-hour strip or 3–5 day cards, not both.
- **Pros**: Simpler layout and less data to present.
- **Cons**: Hourly helps same-day decisions; daily helps week planning—omitting one leaves a gap.
- **Why rejected**: User chose **both** hourly (24h) and daily (3–5 days) in the forecast scope clarification.

## Consequences

### Positive

- Users get actionable context for today and the coming days without leaving the app.
- Disambiguation reduces wrong-city frustration for common place names.
- Geolocation as opt-in chip respects privacy and matches user expectation.
- Backend-only data access keeps a single integration boundary for the frontend.

### Negative

- Larger UI surface and more loading/error states than a conditions-only panel.
- More forecast data increases perceived latency if not presented with clear loading feedback.
- Unit toggle must apply consistently across current, hourly, and daily sections.

### Risks

- **Ambiguous or unknown cities**: Mitigated by disambiguation list and clear empty/error messaging.
- **Geolocation denied or inaccurate**: Mitigated by keeping manual search as the primary path; chip is optional.
- **External data provider availability**: Mitigated by user-visible error states and retry affordance (product-level; implementation in TechSpec).
