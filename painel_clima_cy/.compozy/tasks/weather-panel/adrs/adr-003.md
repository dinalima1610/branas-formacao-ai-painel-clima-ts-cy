# ADR-003: No Server-Side Cache for Open-Meteo in MVP

## Status

Accepted

## Date

2026-05-20

## Context

Open-Meteo is free and keyless. PRD risk table mentions backend caching as a possible mitigation for downtime or rate limits. TechSpec clarification needed an explicit MVP stance.

## Decision

**Do not implement server-side caching** in MVP. Every `/places/*` and `/weather` request triggers a fresh upstream call (subject to normal HTTP client timeouts).

## Alternatives Considered

### Alternative 1: In-memory TTL cache (5–10 minutes)

- **Description**: Cache forecast payloads keyed by lat/lon + unit.
- **Pros**: Reduces duplicate Open-Meteo traffic during demos and unit toggling.
- **Cons**: Stale data risk; invalidation rules; more test surface.
- **Why rejected**: User chose simplest path for course MVP.

### Alternative 2: Split TTL for geocoding vs forecast

- **Description**: Longer cache for stable place names, shorter for weather.
- **Pros**: Balances accuracy and performance.
- **Cons**: Two cache policies to maintain without strong MVP need.
- **Why rejected**: YAGNI for initial delivery.

## Consequences

### Positive

- Fastest implementation; no cache invalidation bugs.
- Weather and unit toggle always reflect live upstream data.

### Negative

- Repeated searches hit Open-Meteo every time (including toggling °C/°F if implemented as refetch).
- Higher exposure to upstream latency or rate limits during live demos.

### Risks

- **Upstream slowness** — mitigate with loading UI and timeouts; user-visible retry (PRD).
- **Rate limits** — mitigate in Phase 2 with TTL cache; document in TechSpec Known Risks.

## Implementation Notes

- Frontend may convert temperatures client-side when toggling units to avoid duplicate `/weather` calls (see TechSpec); wind labels still follow unit (ADR-004).
- Revisit caching in post-MVP if demo reliability metrics fail.
